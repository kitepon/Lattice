# ADR 0199: 最終成果から機能を逆算して工程を作る

- Status: accepted
- Relates: [製品思想](../../PLAN.md)、[ToDo構造検査](0168-todo-structure-is-an-opt-in-graph-overlay-with-completion-gates.md)

## Context

現在のauthoringは、AIがToDoを分けてから工程DAGを登録する。scope-reviewは元の作業仕様とToDoの対応を調べるが、後続ToDoが必要とする機能が前段の成果に含まれるかを表さない。設計メモを読める担当者でも、最終ゴールや後続の用途を知らず、局所のToDoだけを完成させうる。

plan定義後の`todo structure`はcode-dataflowを検査できるが、工程作成時には明示opt-inでもなく、code anchorが未定の機能要求は扱わない。工程の意味をAIに任せる方針を維持しながら、その判断を受け止める契約が必要である。

ゴールは開発中に変わる。旧planを変更不能にすることと、進行中の仕事を修正できないことは同義ではない。旧版を残して後継版を作り、影響されたtaskだけを見直せる入口を工程作成と一体で提供する。

## Decision

1. **最終成果から機能を逆向きに宣言する。** AIはゴールの目的・受入条件から必要な機能を挙げ、各機能の前提機能、提供元、機能自体の受入条件を記録する。機能の提供元は工程、既存機能、又は理由と問いを持つ未知である。
2. **各ToDoの必要・提供機能を一級の契約にする。** 既知の提供元、後続の利用、工程依存を機械が照合する。未提供、孤立、循環、参照先不在をtypedな結果として示す。未知を既知へ丸めず、未知があるだけで工程を登録不能にしない。
3. **全体の目的を担当者へ渡す。** `todo show`と着手結果は全体目的、ゴールの受入条件、担当工程の必要・提供機能、後続の用途、未知を同梱する。担当者に元のMarkdownを探させない。
4. **変更は後継版で受ける。** ゴール、機能、工程の変更を新しいplan versionへ編成し、変わらないtaskの結果は保持する。意味が変わるtaskのreset／退役を明示し、変更と無関係な工程を巻き込まない。逆算工程のauthoringは`lattice.plan_create_input.v4`を初回・追加・変更で共通に使う。後継版は`lattice.phase_todo_revision.v4`へコンパイルし、機能契約を正本とする工程にMarkdown source inventoryとcutoverを要求しない。必要ならAIは`continuity`に理由を付け、既存成果を保持する判断を明示する。
5. **自然文の依頼は操作AIへ導線を渡す。** 対応AI hostのprompt hookは「Latticeで工程作って」という依頼に逆算工程の正規入口を示す。LatticeはAIの代わりに機能を推定しない。

## Consequences

機能が機械可読でも、オーナーのゴールを意味上十分に満たすかの判断は操作AIが行う。検証結果は「宣言した関係に矛盾が無い」という範囲だけを主張する。未知を含む工程も作成でき、担当者は未知と次の問いを見て計画を更新できる。
