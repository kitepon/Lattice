# ADR 0195: 報告の観測時刻は記録より前にしない。経路は空の報告で確かめる

- Status: accepted
- Date: 2026-10-03
- Amends: [ADR 0193](0193-product-owned-runtime-error-reporting.md)（送信の本文の作り方と、送信のcommand）

## Context

ADR 0193の送信を4台で有効にした日に、2つのことが分かった。

1. **故障や解決の直後の自動送信が、受け口に断られる。** Latticeは`observed_at`を、署名の時刻（秒）と同じ値へ
   切り捨てて作っていた。BugHubは、記録の`last_seen`や解決の`resolved_at`が`observed_at`より後の報告を
   422 `invalid_report`で断る。記録と同じ1秒の中で送ると、切り捨てた`observed_at`は記録より前になる。
   自動送信は記録の直後に走るので、ほとんどの場合これに当たる。断られた報告は、同じ中身の送り直しの制限で、
   最大1時間遅れて届く。記録は失われない。最初の到達確認が通ったのは、記録が秒の終わり（.999）で、
   送信が次の秒へまたいだためだった。
2. **Windowsの端末から届くことを、確かめる方法が無い。** 届くことを確かめるには記録が1件要る。
   起きていない故障の記録を作って送れば、受け口の履歴に偽の故障が残り、持ち主へ通知が出る。
   合鍵を入れ替えた時も、次の本物の故障まで、新しい合鍵で届くかが分からない。

## Decision

1. `observed_at`は、送る時刻と、載せる記録の`last_seen`・`resolved_at`のうち、最も後の時刻にする。
   秒へ切り捨てない。署名の時刻`ts`は今までどおり送る時刻の秒で、`observed_at`との差は、端末の時計が
   正しければ1秒に満たない。端末の時計が戻って記録のほうが後になった時は、`observed_at`を記録の時刻まで進める
   ——差がBugHubの許す幅（10分）を越えれば、受け口が時計のずれとして断る。
2. 受け口の検査は変えない。「記録の時刻は`observed_at`以前」はBugHubの契約で、正しい。
3. `lattice runtime-errors reporting verify --json`を足す。記録を載せない空の報告を1通送り、
   合鍵の読み取り・署名・受け口までの経路・受領の署名を確かめる。
   - 送る条件は`report`と同じ。送信を有効にしていない端末と、合鍵の無い端末は、networkへ触れない。
   - storeの記録、受領の印（`acknowledged_through`）、送る時機の記録には触れない。
   - 結果は`verified`（200・`accepted: true`・`report_id`一致・応答の署名一致がそろった時だけ）か、
     `report`と同じ語（`rejected`・`unconfirmed`・`disabled`等）。`verified`の時だけexit 0。
   - 受け口は、空の報告の受領を記録するだけで、issueも通知も動かさない。
4. `reporting verify`の後のCLI実行の終わりでは、自動送信を起こさない。受け口は端末×製品ごとに
   1分に1回まで受けるので、続けて送ると断られる。

## Consequences

- 故障や解決の直後の自動送信が、最初の1回で届く。
- `reporting verify`は受け口の1分に1回の枠を使う。その直後1分以内に故障が起きると、自動送信は429で断られ、
  1時間後（または次の記録の時）に送り直される。
- 手で打つ`report`と`reporting verify`を続けて打つ時は、1分空ける。

## Acceptance

- 記録や解決と同じ1秒の中で送った報告を、BugHubと同じ規則で検査する受け口が受領する。
- 端末の時計が戻った時、`observed_at`は記録の時刻になる。
- `reporting verify`は空の配列だけを載せ、確かめる前後でstoreの診断と送信の状態が変わらない。
- 送信を有効にしていない端末と合鍵の無い端末では、`reporting verify`が受け口へ1回も接続しない。
